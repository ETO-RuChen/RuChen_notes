# 第 1 课：从源文件到可观察结果

本课只建立两个心智模型：**嵌入式系统与主机的运行环境不同**，以及**源文件到可观察结果的最小闭环**。代码是主机示例，待主机验证；没有开发板或运行记录，因此不表示已经上板。

## 1. 本节目标

完成本课后，你应该能：

1. 说明为什么不能把主机程序拥有的条件直接当成嵌入式程序也拥有的条件。
2. 说出并亲手走通 `源文件 -> 构建产物 -> 运行 -> 可观察结果`。

预计用时 30 分钟。本课不要求任何 C 语言、构建系统或单片机前置知识。

## 2. 它解决什么问题

在 Windows 上运行程序时，我们习惯了屏幕、终端和操作系统已经存在。嵌入式系统（embedded system，嵌入到设备中完成特定任务的计算系统）的目标环境可能没有这些条件。具体目标到底提供什么，必须由开发板资料和工程配置确认，不能从主机经验猜测。

另一方面，初学者常把“写完代码”当成“程序已经工作”。源文件只是输入；只有得到可运行文件、实际运行，并观察到结果，才形成最小验证闭环。

## 4. 核心原理

### 模型一：主机环境不等于嵌入式环境

- **解决的问题**：阻止程序依赖目标设备并不存在的条件。
- **条件在哪里定义**：主机条件由 Windows 和终端提供；目标条件应在具体硬件资料与工程配置中确认。
- **谁持有条件**：当前实验由主机持有终端和可执行文件；未来目标设备持有处理器、存储器及实际可用的输入输出资源。
- **谁提供条件**：本课由 Windows、GCC 和学习者输入的命令共同提供；迁移时由目标硬件、工具链和工程配置提供。
- **调用如何流动**：学习者输入命令，主机启动程序，程序把结果交回终端；迁移后，结果必须改由目标设备实际具备的观察通道交出。

因此，不要先问“这段主机代码能否原样放进单片机”，而要先问“它依赖了哪些运行条件，目标是否提供”。ST 的 STM32CubeIDE 官方手册把构建、运行和调试 STM32 工程列为开发工具职责，也表明主机开发工具与目标程序是工作流中的不同位置。[1]

### 模型二：源文件到可观察结果的最小闭环

- **解决的问题**：把“我写了代码”变成可检查的事实。
- **对象在哪里定义**：程序规则写在 `main.c`；输出文件名写在构建命令中；预期结果写在实验步骤中。
- **谁持有对象**：学习者持有源文件，文件系统持有构建产物，运行中的程序持有本次计算结果。
- **谁提供输入**：学习者把 `main.c` 和选项交给编译器；主机在运行时提供执行环境。
- **调用如何流动**：`main.c -> GCC -> lesson.exe -> Windows 运行 -> 终端文本与退出状态`。

GCC 官方文档说明，一次普通调用会完成得到最终程序所需的处理阶段；本课只使用这个整体能力，不展开内部阶段。[2]

## 6. 从输入到结果的完整流程

## 9. 最小代码示例

将以下内容保存为 `main.c`：

```c
#include <stdint.h>
#include <stdio.h>

int main(void)
{
    uint32_t input = 40U;
    uint32_t result = input + 2U;

    printf("result=%lu\n", (unsigned long)result);

    if (result != 42U) {
        return 1;
    }

    return 0;
}
```

这是 C11 子集示例，不使用动态内存。`uint32_t` 表示宽度固定为 32 位的无符号整数；`input` 保存输入，`result` 保存计算结果；`printf` 把文本交给主机终端；`if` 在结果不等于 `42` 时返回失败状态。这里不展开这些语法的通用规则。

代码属于本课的主机验证层，只依赖 C 标准库和主机运行环境。

## 10. 常见错误

- **只保存源文件就宣布完成**：还缺少构建、运行和观察。
- **只看见 `result=42`**：还应检查退出状态是否为 `0`。
- **命令找不到 `gcc`**：先处理工具可用性，不要随意改代码。
- **把主机输出当成上板结果**：本实验没有硬件证据。
- **把 `.exe` 当成单片机产物**：它是为当前 Windows 主机生成的文件。

## 11. 调试观察点
