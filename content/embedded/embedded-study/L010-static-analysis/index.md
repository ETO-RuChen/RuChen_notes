# 第 10 课：用静态分析回溯可能的空指针路径

编译成功只能说明工具接受了代码，不代表每条可能路径都安全；只运行一组输入，也可能绕开风险。本课先人工预测一条“返回空指针后继续解引用”的路径，再让 GCC 静态分析器在**不运行被分析程序**时寻找它。分析器报告是待核对的风险证据，不是程序正确性证明。

## 1. 本节目标

学习者能在 Windows 主机上对一个无动态内存的最小 C11 源文件运行 GCC 静态分析器，说明分析器何时读取什么代码，沿条件、返回值和解引用点回溯一条可能路径，并通过受控修复复查报告。预计用时 30 分钟。

本课只引入计划规定的两个新核心概念：

1. **静态分析在不执行程序时沿可能路径发现风险**。
2. **静态分析诊断需要回溯到代码路径并以证据处理**。

## 2. 它解决什么问题

普通编译会完成语法、类型等检查，但一次成功编译不能证明所有可能输入都安全。主机运行也只覆盖实际走过的路径。静态分析器（static analyzer，静态分析工具）读取源代码及工具可见的调用关系，推断可能到达的状态，在程序运行前提示风险。

GCC 15.2.0 手册说明，`-fanalyzer` 会分析程序流并寻找跨函数的“有意义路径”；它并非完备或可靠的证明系统，可能产生误报（false positive，报告了实际约束下不会发生的风险）和漏报，因此定位是找缺陷而非证明程序正确。[1]

## 3. 必要前置知识

本课沿用已完成的 C11 最小程序、固定宽度整数、指针、`const`、存储期、链接属性、编译器和主机构建调用。不假定你知道控制流图、符号执行、MISRA C、覆盖率、动态检测、交叉编译或 STM32 硬件。

空指针（null pointer）是不指向有效对象的指针值。空指针解引用（null-pointer dereference）是通过它读取或写入对象；本课只把它作为一条易观察的受控风险路径，不扩展指针课程。

## 4. 核心原理

GCC 在收到 `-fanalyzer` 后，会在编译期间分析当前可见的 C 代码，尝试串起条件分支和函数调用。GCC 15.2.0 明确把它称为对代码的符号执行，并说明分析成本高于普通告警；`-Wanalyzer-null-dereference` 针对“已知为空的值在某条路径上被解引用”，而 `-Wanalyzer-possible-null-dereference` 针对“可能为空”的路径。[1]

可能执行路径（possible execution path）是条件和调用关系允许经历的一条路线，不等于这条路线已经在主机或硬件上发生。分析器也会做取舍，所以有报告时要回溯证据；没有报告时仍不能推出“没有缺陷”。

风险处置（triage，风险分类与处理）不是清空告警数量，而是回答：哪个条件成立、哪个函数返回了什么、哪个使用点产生风险、修复后路径是否被代码边界阻断。怀疑误报时也要记录实际约束的证据，不能凭直觉忽略。

## 9. 最小代码示例

分析前先预测：`main` 传入 `1U`；`find_value` 只有在键为 `0U` 时返回有效地址，因此返回 `NULL`；`app_read` 没有检查便执行 `*value`。

`app.c` 属于应用示例层。`values` 具有静态存储期，`value` 是调用期间存在的局部指针；依赖只指向 C 标准头，不使用动态内存：

```c
#include <stddef.h>
#include <stdint.h>

static const uint32_t values[1] = {42U};

static const uint32_t *find_value(uint32_t key)
{
    if (key == 0U) {
        return &values[0];
    }
    return NULL;
}

int32_t app_read(uint32_t key)
{
    const uint32_t *const value = find_value(key);
    return (int32_t)(*value);
}

int main(void)
{
    return (app_read(1U) == 0) ? 0 : 1;
}
```

受控修复只改变使用边界，在解引用前判断：

```c
int32_t app_read(uint32_t key)
{
    const uint32_t *const value = find_value(key);
    if (value == NULL) {
        return -1;
    }
    return (int32_t)(*value);
}
```

修复阻断了本课预测的空指针解引用路径，但不证明整个程序正确。

## 10. 常见错误

- 把 `-Wall -Wextra` 与 `-fanalyzer` 当成同一种检查；GCC 手册把额外静态分析作为单独选项说明。[1][2]
- 只数告警，不看条件、返回值与解引用点。
- 把特定告警文字、编号、退出状态或目标文件生成情况当成跨版本保证。
- 看到诊断消失就宣布修复正确，没有比较源码、命令和输入散列。
- 用“我认为不会传入 1”判定误报，却没有调用方约束或测试证据。
- 把主机分析结果误写成构建、运行或上板已经完成。

## 11. 调试观察点

1. 版本：保存 `gcc --version`；`-fanalyzer` 还要求该 GCC 构建启用了分析器支持。[1]
2. 输入：记录 `app.c` 的 SHA-256 散列，避免比较到不同源码。
3. 命令：完整记录语言标准、告警、分析器和 `-c` 选项。
4. 路径：在实际输出中找条件分支、`find_value` 返回点和 `*value` 使用点；措辞以本机结果为准。
5. 状态：紧接命令记录 `$LASTEXITCODE`。告警是否导致非零状态取决于诊断策略；例如 GCC 的 `-Werror` 才会把告警转成错误。[2]
6. 产物：检查日志和 `app.o` 是否存在，但不要预设一定生成。
