# 第 11 课：复位序列：从规定入口到应用入口

嵌入式目标在复位后不会由主机操作系统直接调用 `main`。处理器会先按架构规定的启动路径取得一个入口，再由复位处理程序完成必要的边界工作，最后才进入应用代码。本课只建立这个可迁移的控制流模型，不展开向量表条目格式、启动文件、链接脚本、栈堆、寄存器或具体 STM32 型号。

## 1. 本节目标

完成本课后，你应能：

- 用自己的话描述“复位 -> 取得入口 -> 复位处理程序 -> 必要初始化边界 -> 应用入口”的顺序。
- 区分目标硬件的复位启动路径与主机运行环境直接调用 `main` 的路径。
- 用一个 Host Fake（主机替身）记录事件顺序，并说明它没有模拟真实硬件复位。

本课预计 30 分钟，只引入一个新核心概念：**复位序列**，即处理器复位后按固定启动路径取得入口并开始执行应用。

## 2. 它解决什么问题

程序总要回答“第一条应用指令从哪里来”。在主机上，操作系统和 C 运行环境已经准备好进程，再把控制权交给 `main`；在嵌入式目标上，复位意味着处理器刚开始重新取得执行控制权，必须先遵循处理器规定的入口约定。若把两者混为一谈，就会把主机实验中的显式 `main()` 调用误认为硬件复位行为，也会在没有证据时猜测地址、寄存器或启动文件细节。

ST 的 STM32F7 编程手册和参考手册用于核对本课所需的复位入口、异常入口与应用入口边界。[1][2] 这些资料覆盖 F7 工程和处理器实现背景；本课只提取可迁移的控制流模型，不把 F7 的具体布局或实现细节推广到所有芯片。

## 4. 核心原理

### 4.1 复位序列是一个控制流边界

复位序列解决的是“处理器重新开始执行时，谁先获得控制权”。可以把它抽象为五个事件：

```text
复位发生
  -> 处理器按规定方式取得入口
  -> 进入复位处理程序
  -> 完成必要初始化边界
  -> 转入应用入口
```

这不是一条由 `main` 自己发起的普通函数调用链。入口由处理器的启动约定提供，复位处理程序是目标工程实现的代码对象，应用入口是随后由该处理程序转入的应用代码。

### 4.2 每个对象由谁定义、持有和触发

| 机制 | 解决的问题 | 定义位置 | 谁持有/提供 | 谁触发 | 调用如何流动 |
| --- | --- | --- | --- | --- | --- |
| 规定入口 | 复位后从哪里开始 | 处理器架构和目标启动约定 | 处理器按架构读取并提供控制权 | 复位事件 | 复位 -> 规定入口 |
| 复位处理程序 | 把启动边界连接到应用 | 目标工程的启动实现（本课不展开文件形式） | 程序映像包含该代码 | 处理器转入入口后执行 | 入口 -> 处理程序 |
| 必要初始化边界 | 让应用获得约定的执行前提 | 启动实现与运行环境约定 | 处理程序维护顺序 | 处理程序内部步骤 | 处理程序 -> 初始化边界 |
| 应用入口 | 开始应用自己的控制流 | 应用代码 | 应用代码和其静态对象 | 处理程序完成边界后转入 | 初始化边界 -> 应用入口 |

这里的“持有”表示谁负责保存或提供该对象，不表示动态内存所有权。本课没有动态内存，也没有依赖注入。

### 4.3 主机的 `main` 不是硬件复位入口

主机实验通常由 C 运行环境准备进程，然后调用 `main`。因此实验代码中看到的 `main()` 是**测试驱动的显式调用**或由主机运行环境发起的调用；它只能帮助我们观察一个抽象顺序，不能证明目标处理器真的经历了复位、取得入口或执行了某种地址布局。

## 9. 最小代码示例

这是一个 C11 子集的概念模型。它没有函数指针、动态内存、寄存器或具体硬件地址。`reset_handler` 和 `app_entry` 是示例中的代码对象；`main` 只是主机实验驱动。

```c
#include <assert.h>
#include <stdint.h>

enum event_id {
    EVENT_ENTRY_OBTAINED = 1,
    EVENT_INIT_BOUNDARY = 2,
    EVENT_APP_ENTRY = 3
};

static uint32_t event_log[3];
static uint32_t event_count;

static void record_event(uint32_t event)
{
    if (event_count < 3U) {
        event_log[event_count] = event;
        event_count += 1U;
    }
}

static void app_entry(void)
{
    record_event(EVENT_APP_ENTRY);
}

static void reset_handler(void)
{
    record_event(EVENT_ENTRY_OBTAINED);
    record_event(EVENT_INIT_BOUNDARY);
    app_entry();
}

int main(void)
{
    reset_handler();

    assert(event_count == 3U);
    assert(event_log[0] == EVENT_ENTRY_OBTAINED);
    assert(event_log[1] == EVENT_INIT_BOUNDARY);
    assert(event_log[2] == EVENT_APP_ENTRY);
    return 0;
}
```

代码层次是：枚举、日志和函数属于单文件的教学示例层；静态数组由程序自身持有；`main` 显式触发 `reset_handler`，所以这里的顺序是**逻辑验证**，不是硬件启动证据。若把 `record_event(EVENT_INIT_BOUNDARY)` 与 `app_entry()` 调换，断言仍可能通过数量检查但顺序断言会失败；这说明实验能观察顺序，却不能观察处理器内部真实动作。

## 11. 调试观察点

1. **事件顺序**：逐行查看 `event_log`，确认记录顺序，而不是只看最终返回值。
2. **调用栈**：在 `app_entry` 设置断点，观察主机调用栈为 `main -> reset_handler -> app_entry`；这只是主机函数栈。
3. **边界注释**：在调试笔记中单独写出“主机显式调用”和“目标复位触发”，避免混用。
4. **失败注入**：暂时调换两个 `record_event` 调用，确认断言能够发现顺序错误，再恢复示例。
5. **证据分类**：记录编译器输出或主机运行输出时，标注为 Host Fake 证据；不要把它放入硬件证据。
